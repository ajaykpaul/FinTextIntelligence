Evaluation report: shared-xlmr.v4.1
===================================

Current release: shared-xlmr.v4.1. Result: not accepted. Of the 14 gated criteria, 5
pass on their point estimate, 6 fail on measurement and 3 can't be measured before a
pilot. Of the 5 passes, the 3 model metrics sit inside their own 95% interval: on
another test set of the same kind they could as easily fail (section 1, Intervals). This
report says which is which, and why each failure happened, because "not accepted" covers
very different situations: some targets miss by a hair, some are blocked by hardware,
and one may not be reachable on its test data at all.

v4.1 is v4 plus Arabic sentiment offsets tuned on dev, and only Arabic sentiment differs
between the two. The sections below keep the history from v2 onward, because what each
change did and didn't do is the evidence for the current numbers: section 1 for the
model, section 3 for latency.

1. Model quality
----------------

What the thresholds are

Toxicity is tuned recall-first: the threshold keeps dev recall at 0.90 and takes the
best F1 above that. The PRD also asks for 0.90 precision; for both languages no
threshold met both, so recall won and the result is marked infeasible.

  Threshold             Value   Dev precision   Dev recall   Dev F1   Best F1, any threshold
  --------------------- ------- --------------- ------------ -------- ------------------------
  Toxicity, English     0.633   0.733           0.913        0.813    0.813
  Toxicity, Arabic      0.216   0.551           0.905        0.685    0.748
  Misleading, English   0.365   0.774           0.875        0.821    0.821

The last column matters more than the gate. Neither toxicity F1 target is reachable by
choosing a threshold: the best dev F1 at any threshold is 0.813 for English (target
0.85) and 0.748 for Arabic (target 0.80). Only a better model or cleaner labels can move
them.

Where the toxicity errors are

model of this series; the full table and its reading are in ARABIC_TOXICITY.txt.

- OSACT4 alone passes the Arabic AUROC gate (0.942). OSACT5 (0.854) pulls the combined
  figure under 0.92, and the model underfits it even on its training rows.

Comparing two runs

Separate intervals are the wrong tool for "is run B better than run A". Both runs find
the same rows hard, so most of the resampling noise is shared; looking at whether two
separate intervals overlap ignores that and misses real differences.
fintext compare <run A> <run B> resamples the test rows once per draw, scores both runs
on that same draw, and puts the interval on B − A. Each run keeps its own dev-tuned
thresholds, so the question is whether B as deployed beats A as deployed. The call is "B
better", "A better" or "no detectable difference" (the interval on the difference
contains zero); for the gap, lower is better.

It refuses to pair runs unless they were tested on the same rows, checked by a per-row
key (a digest of language, source and text; no text is stored) and by the labels. Runs
whose splits differ can be compared with --common-rows on the rows both held out for
test; those rows were unseen by both models, so the comparison is still fair, only
smaller. Run 1 and run 2 share their split, so the result above is fully paired.

Arabic sentiment

Arabic sentiment is trained on machine translations of the English financial sets and
tested on ArSAS, native tweets (9,339 test rows: 37% negative, 37% neutral, 23%
positive). The head almost never answers "neutral" on them: run 2 predicts it 1,174
times against 3,441 true, and neutral F1 is 0.30 (0.14–0.40 across runs and seeds).
Almost all of the seed-to-seed spread in Arabic sentiment (0.425–0.490) is that one
class. English neutral F1 is 0.85, so the head can learn the class; it learnt the
translated-financial version of it.

Two explanations predict different things. If the neutral probability still ranks
neutral tweets above the rest but sits too low, a per-class offset chosen on dev fixes
it, as a threshold does for toxicity. If it doesn't rank them, no decision rule can.
fintext.sentiment_offsets measures both (reports/arabic_sentiment_offsets.json):

  Offsets tuned on ArSAS dev (log scale; negative fixed at 0)   positive −0.6, neutral +1.2   positive −1.1, neutral +0.6
  Test macro-F1 without -> with offsets                          0.490 -> 0.569                 0.484 -> 0.572
  Paired difference, 95% interval                               +0.078 (+0.069 to +0.087)     +0.088 (+0.078 to +0.098)
  Neutral F1 with offsets                                       0.53                          0.53

Both, then. The offsets recover about eight points on both runs, tuned on dev and
applied to test unchanged, so part of the problem is calibration. But neutral AUROC of
0.64–0.68 is weak ranking: the head barely separates neutral tweets from opinionated
ones, and no offset changes that. The rest needs native, in-domain Arabic sentiment in
training. Using ArSAS dev to choose three numbers does make ArSAS less of an untouched
check than it was; the test half is still never used for any choice.

The 0.595 noted for an earlier zero-shot run was on a different split, so it isn't
comparable to these numbers and isn't used here.

Shipped as shared-xlmr.v2.1. The offsets are a decision rule for one artefact, like its
thresholds, so they are registered with it: v2.1 is the same ONNX file as v2 plus Arabic
offsets (positive −0.6, neutral +1.2), with v2 as its parent
(fintext sentiment-offsets). The service adds them to the sentiment logits for Arabic
only and renormalises, so the confidence floor still reads a probability. On 400 ArSAS
test tweets the served model's label matched the offline decision on all 400, for both
versions. Registered, not promoted: promotion is still blocked by latency (section 3),
not by this.

The ranking problem is what changed. Neutral one-vs-rest AUROC goes from 0.678 (run 2)
to 0.905–0.918 across the v3 seeds, and positive and negative from 0.79 / 0.74 to 0.87 /
0.92. The v3 seeds also agree with each other far better than the v2 seeds did: a spread
of 0.008 against 0.065. Nothing else was harmed. English toxicity AUROC is three
thousandths higher, too small to matter, and Arabic toxicity doesn't move, as expected,
since no toxicity data was added.

Is the gain real? A jump this size calls for checking for leakage first. Each ArSAS test
tweet was compared with every ArSarcasm-v2 tweet by character 3–5-gram TF-IDF cosine.
The highest match is 0.585, and only 4 of 9,339 are at or above 0.5. The top matches are
YouTube "added a video to a playlist" boilerplate, not the same tweet. With those 4
removed, every run's macro-F1 is unchanged to three decimals. fintext leakage-check
(reports/v3_leakage_check.json) repeats this over every Arabic test row, toxicity tweets
included, against the 15,542 rows actually trained on. 19 of 13,627 are at or above 0.5.
They are stock phrases ("good morning", "there is no power but God", laughter), not
copied tweets, and removing them moves no metric by more than 0.0007. So the gain is not
the test set leaking into training; it is what native in-domain labels teach. The two
datasets come from different collections: ArSarcasm-v2 is re-annotated from earlier
tweet sets such as ASTD and SemEval-2017, and ArSAS comes from its own topic-driven
crawl.

Offsets on v3 are almost redundant. Re-tuned on each seed's own dev scores, they add
+0.004, +0.013 and +0.006 on test; only the middle one is clear of zero. The tuned
values also disagree between seeds (neutral −0.2, +0.5, 0.0), which fits there being
little left to calibrate. Against v2.1, run 2 with its offsets (0.569), each v3 seed
with its own offsets scores 0.736–0.751. That is +0.167 to +0.182, with every paired
interval clear of zero. Neutral F1 with offsets is 0.77–0.79, against 0.53 for v2.1.

2. Provenance
-------------

Replayed against cases built from real SEC filings (fintext replay-set). A genuine claim
is the sentence of a company's own Exhibit 99.1 press release that names it and states
the event, paired with the 8-K it was filed with. A fabricated claim is a copy with the
company swapped for one whose filings can't support it, and which names no company that
really filed about that kind of event nearby.

  Set           Filed                Genuine   Fabricated   Used for
  ------------- -------------------- --------- ------------ -----------------------------------------
  Development   2022-01 to 2024-06   125       100          finding and fixing failures
  Test          2024-07 to 2025-12   115       97           this report, run once after development

The two sets share no filing; fintext replay --disjoint-from checks that and refuses to
run otherwise.

Result on the test set

The index the service uses now holds each filing's text (fintext edgar --with-text), not
only its 8-K item titles, so the replay gives every filing the same text: the first
4,000 characters of the same document, fetched from the same URL
(fintext replay-set --add-text). The claims and labels are unchanged.

Each genuine claim was taken from its own filing, so a filing with text contains the
claim almost word for word, which flatters recall. The headline row therefore removes
each claim's own sentence from its filing first (fintext replay --hold-out-claim): the
rest of the release has to support it, as it would a paraphrase in the news. That
removed 91 of 115 sentences; the other 24 fall past the 4,000 characters kept, so they
were never there to match.

  Test set (115 genuine, 97 fabricated)   Genuine confirmed   Fabricated confirmed   Precision (95% lower bound)
  --------------------------------------- ------------------- ---------------------- -----------------------------
  Item titles only (previous index)       43                  0                      1.0 (0.918)
  With filing text                        80                  0                      1.0 (0.954)
  With text, claim sentence held out      72                  0                      1.0 (0.949)

Claim-extraction recall is 0.934 in every row (it depends on the claim, not the filing).
Before the item-3 work it was 0.665, with 33 genuine claims confirmed.

The precision gate held throughout. Its lower bound is 0.949 on the headline row, so 72
confirmations are not quite enough to show 0.95 even with no errors; that needs a larger
set. Coverage is now 72 of 115: the remaining 43 are recognised and left pending or
uncorroborated, mostly because the rest of the release doesn't repeat any particular of
the claim (next section, item 6). Scored once, after the development work below.

What changed, and how it was found

Everything below was found and fixed on the development set. The test set was scored
once, at the end. One caveat on that separation: the kinds of failure were first seen on
the test set's earlier run, so the work was aimed at them; every specific rule was
written and checked against the development set only.

1.  The replay measured a weaker extractor than the one deployed. The service builds its
    company vocabulary from the filing index (pipeline.py); the replay used a seven-name
    table. The replay now does what the service does. This was a measurement bug, and
    accounts for much of the recall change.
2.  Tickers were matched in any case. With the index vocabulary in use, Agilent's ticker
    "A" matched the article "a" in every sentence, and outranked the real company. This
    was live in the service. Tickers and acronyms now match only as written, and names
    only where they're capitalised.
3.  Claim phrasing. Guidance verbs with words in between ("raised total company
    guidance", "raising our full-year revenue and earnings outlook"), exchange
    compliance notices ("deficiency letter", "delisting determination"), and longer
    contract descriptions.
4.  Generic filing words could confirm the wrong kind of claim. Once the extractor
    recognised more companies, two fabricated contract awards on the development set
    were confirmed by the same companies' acquisition filings: "item 1.01" and
    "agreement" were enough. A filing now needs at least one word specific to the claim
    type. This costs genuine confirmations wherever the only evidence is an item title,
    which is the right side to err on.
5.  Fabricated-case labels. One development-set "fabrication" still named the real
    acquirer of the deal it described, so confirming it was correct. The builder now
    rejects any fabrication that names a company with a genuine filing of that kind
    nearby. Both sets were regenerated with the rule (no case in the test set was
    affected).
6.  Filing text let unrelated filings confirm fabricated claims. With text indexed,
    three fabricated development claims were confirmed by the named company's own
    filings about something else: an earnings release that mentioned guidance confirmed
    a guidance quote from another company's chief executive, and a filing about one
    acquisition confirmed a fabricated acquisition of a different target. Company, claim
    type and date all matched; nothing particular to the claim did. A filing with text
    must now also mention one of the claim's particulars: a name other than the
    company's (a counterparty, a person) or an amount. Filings with only item titles
    can't, so they are judged as before; the item-titles-only test result is
    byte-for-byte unchanged. This was live in the service as soon as the index held
    text. It cost 7 of 82 genuine development confirmations.

Development numbers (125 genuine, 100 fabricated): item titles only 47 confirmed; with
text 82 genuine and 3 fabricated before change 6, 83 and 0 after; with the claim held
out, 74 and 0.

Each change has unit tests (tests/test_claim_extraction.py, tests/test_replay_set.py,
tests/test_edgar.py).

What it can't measure

Pending resolves before expiry: a press release is filed with its 8-K, so claim and
evidence appear together. Measuring it needs news timestamped before the filing.

Other fixes from the replay

The replay engine checked every claim before delivering any document, which is wrong for
any replay longer than one window; it now runs in time order. The EDGAR index builder
mis-parsed filers with more than one listed class ("(BNZI, BNZIW)"). Both are fixed with
regression tests. The shipped provenance index
(artifacts/provenance/primary_index.jsonl) was rebuilt after the fix: 848 filings, 437
with a ticker; entries with ticker text left in the company name went from 82 to 2, both
of them genuine parts of a legal name.

3. Service level
----------------

Measured on an Apple M5 (10 cores), ONNX Runtime 1.30, fp32, 4 intra-op threads, full
pipeline, inputs padded to 256 tokens (reports/bench_v2_c1.json, _c2.json).

  Concurrency   p50       p95       p99       Throughput
  ------------- --------- --------- --------- ------------
  1             50.4 ms   58.0 ms   61.2 ms   18.8 rps
  2             52.6 ms   60.5 ms   65.8 ms   33.5 rps

Re-measured with v3 (reports/bench_v3_vs_v2.json). The setup is the same as above, but
v2, v3 and v3.1 were run alternately in two rounds in one session, so all three saw the
same machine conditions:

  Version   p95, concurrency 1   p95, concurrency 2   Throughput (c1 / c2)
  --------- -------------------- -------------------- ----------------------
  v2        51.2, 49.5 ms        49.8, 49.7 ms        23 / 34 rps
  v3        50.4, 50.0 ms        50.3, 50.3 ms        23 / 33–34 rps
  v3.1      49.7, 50.1 ms        50.7, 51.4 ms        23 / 33–34 rps

- v3 is no faster or slower than v2. It is the same architecture at the same precision,
  and the offsets in v3.1 are three additions. The model-only gap at export (47.6
  against 50.5 ms) was run-to-run noise.
- v2 now measures about 50 ms, not 58. That is v2 itself measured again, not a new
  model, so the 58 ms reflected machine conditions at the time (background load or heat;
  the cause wasn't recorded). The honest reading: on this Mac the full-pipeline p95 sits
  right at the 50 ms target, landing either side of it from run to run. It doesn't pass
  the target with any margin.
- Throughput still fails clearly, at 33–34 rps against 100.

So the conclusion below is unchanged.

Model alone, by input length: 256 tokens p95 47–50 ms on 4 threads (61 ms on one); 64
tokens 14 ms; 32 tokens 9 ms. Real headlines are nearer the short end.

Why the targets miss here. The PRD's latency and throughput budgets assume an int8 model
on an x86 server. On this ARM machine:

- int8 failed the parity check: it moved misleading scores by up to 0.099 and sentiment
  by 0.069 against a 0.05 tolerance, so thresholds tuned on the float model would not
  have carried over. Per-channel quantisation and keeping the heads or the last 2–4
  layers in fp32 all failed too.
- int8 was also slower than fp32 here (p95 79 ms against 62 ms single-thread).

So the served artefact is fp32, and the measurement is not on the reference hardware.
The registry's latency gate refused to promote it (model-only p95 50.5 ms), and it was
not forced.

int8 on x86, measured. Notebook step 11 exported the v4 weights on a Colab Intel Xeon
(2.2 GHz, 12 vCPUs, AVX-512 VNNI), with the same ONNX Runtime 1.30 as the Mac. The fp32
export matched the run's own scores within 4e-6, so any shift is quantisation, not
export.

Eight dynamic int8 recipes were then compared with fp32 on 1,000 held-out rows, 500
Arabic and 500 English, counting the decisions that flip at v4.1's thresholds and
offsets. The data is in reports/int8_x86_colab.json, int8_x86_variants.json and the two
ARM files.

  Recipe                  What's quantised                                Flips on x86 (toxicity / misleading / sentiment)   Flips on ARM   x86 speed-up, 1 / 4 threads
  ----------------------- ----------------------------------------------- -------------------------------------------------- -------------- -----------------------------
  int8 (default)          everything                                      41 / 48 / 90                                       23 / 31 / 43   2.23× / 1.87×
  per-channel             everything, per-channel weights                 46 / 38 / 99                                       21 / 17 / 39   not timed
  int8_reduce_range       everything, 7-bit weights                       73 / 58 / 118                                      62 / 43 / 89   2.25× / 1.86×
  uint8_weights           everything, unsigned weights                    48 / 41 / 81                                       50 / 37 / 77   0.99× / 0.97×
  encoder_linear_only     72 encoder linears; embeddings and heads fp32   51 / 43 / 85                                       28 / 28 / 39   2.25× / 1.86×
  ffn_only                24 feed-forward linears                         48 / 46 / 92                                       15 / 23 / 37   1.64× / 1.47×
  ffn_only_reduce_range   the same, 7-bit                                 51 / 58 / 82                                       39 / 43 / 72   1.64× / 1.45×
  ffn_up_only             12 first feed-forward linears                   12 / 17 / 33                                       11 / 7 / 23    1.17× / 1.11×

Every recipe fails the five-sentence probe check. The closest is ffn_up_only, at 0.055
against 0.05.

What this shows:

- The speed is real on x86. Default int8 roughly halves model-only p95 at 256 tokens:
  488 -> 219 ms on 1 thread, 151 -> 79 ms on 4. On ARM the gain was only about 1.25×.
  Colab's vCPUs are about 3× slower than the M5, so only the ratio transfers, not the
  absolute times.
- The accuracy isn't there. On x86, default int8 flips 9% of sentiment labels and 4–5%
  of toxicity and misleading flags, about twice as many as on ARM.
- The x86 fixes don't help. reduce_range is worse on both architectures, and unsigned
  weights lose the speed. So the error isn't integer overflow.
- Embeddings and heads aren't the cause. Keeping them fp32 changes nothing measurable.
- Speed and accuracy pull against each other. The layers that buy the speed-up are the
  ones that damage decisions: the attention projections, and the second feed-forward
  layer, whose inputs vary the most. Quantising only the first feed-forward layer keeps
  decisions closest, but it still flips 3.3% of sentiment labels on x86 and gains only
  1.1×.

So dynamic post-training int8 is ruled out for this model. What could still reach the
targets is larger work:

- outlier-aware quantisation: SmoothQuant-style static calibration, or
  quantisation-aware fine-tuning;
- a smaller distilled encoder;
- a different latency budget or serving hardware.

Until then the service stays fp32, and the latency and throughput gates stay failed.
